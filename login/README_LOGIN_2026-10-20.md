# Login window — v1.19

The header Login link opens one native modal over the current page. Its black background, white border/text, Orchestra/Club tabs, input sizes and bottom actions follow the supplied reference. The selected tab is white with black text. Close and Escape return to the page and restore focus; closing the direct `/login/` entrance returns home. Native modal behavior keeps keyboard focus inside the window.

Username is the account's email address. Orchestra uses the existing project and admin/internal profiles through `app.js`. Club uses a different project, `club_profiles`, and its own client through `club/club.js`. Their storage keys, passwords, logout and portals are independent. Basic and expired paid Club members can sign in; their current benefits are determined by the verified profile and expiry. Invalid profiles are signed out of the selected system only. Passwords are cleared when switching tabs or closing. Loading prevents duplicate login requests. A signed-in tab offers its own portal link. The Club tab also offers password recovery.

Not a member yet? links to `/opportunities/`. Free Membership Basic registration lives at `/opportunities/club/#club-registration-form`; the old registration fragment is retained as an anchor. Registration forms stay disabled until their handlers are ready and do not fall through to native submissions. Paid plan selection, Stripe checkout and billing now live only inside the authenticated Club portal. Confirmation and recovery emails return there too.

The previous `/internal-login/` and `/membership/` screens are gone. Forwarding documents preserve old bookmarks, query strings and fragments. They do not turn an old-project token into a new Club account. Reissue legacy Club invitations from the new project when migrating members. Portal guards lead to `/login/?account=orchestra` or `/login/?account=club`. **This release requires Club Supabase setup:** follow `../supabase/club/SETUP.md`. The old orchestra schema/functions remain available, and no database changes have been run remotely.

Events now has Ongoing/Past hover, keyboard and touch submenu entries. They select the corresponding left-bar category through `/events/#ongoing-events` and `/events/#past-events`. Ongoing retains the existing current/future/undated-announcement grouping; Past uses earlier Asia/Shanghai dates. The former `#upcoming-events` fragment is still supported.

Checks use the actual frontend and function scripts with mocked authentication and Stripe responses, plus the migration in an embedded PostgreSQL database. They cover independent clients, Basic signup, email confirmation/recovery, portal/role boundaries, isolated logout/password changes, payment identity/price checks, transactional and duplicate fulfillment, loading/errors, and existing navigation/contact/shop behavior. No live email, login, payment or database change was sent. Browser visual QA remains unavailable.
